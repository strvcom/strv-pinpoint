| 2026-06-10 | Architecture | **Overlay dev hot loop** (TASK-22). `pnpm dev:overlay` runs esbuild `--watch` (writing `packages/core/dist/overlay.iife.js`, gitignored) alongside the bridge started with `PIN_DEV=1`; the bridge `fs.watch`es that file (debounced ~80ms) and calls a new `page.reinject(preamble, source)` over the **held CDP connection** — no bin rebuild, no bridge restart, no Chrome reopen. Enabled by a `window.__pinpointTeardown` contract in `index.tsx`: Preact `render(null, mount)` (runs every `useEffect` cleanup → picker/screenshot/escape/positioning/pointerup/link listeners) + `host.remove()` + disposers returned by `installSelectionProbe`/`installBridgeLink` (the latter closes the SSE `EventSource`) + clearing the `__pinpointOverlayInstalled` guard. `reinject` also swaps the `addScriptToEvaluateOnNewDocument` registration so a manual reload uses fresh code. esbuild stays a build-time tool — the watcher is reached via a dynamic `import()` only under `PIN_DEV`, and pulls in only Node builtins, so `bin/pinpoint` keeps zero runtime deps. Live-verified on examples/vite-react (edit orb color → `overlay re-injected`, 0 failures) + unit tests (teardown leaves 0 hosts/balanced listeners; re-inject after teardown = exactly one overlay; watcher debounce coalesces). | Vite HMR is impossible for the overlay (it's an injected string, opaque to the target app's bundler), so re-injection is the model — but a naive re-inject is a silent no-op (the install guard) or stacks a second overlay (old host + document listeners survive). The teardown contract is the enabling piece. State resets on reload (v1) — re-picking is one click; hydration deferred. Caveat: startup does one redundant re-inject (esbuild's first watch build fires the watcher right after the bootstrap inject) — harmless, teardown prevents stacking. |

After a *confirmed* reload (a post-inject sentinel global was wiped + `timeOrigin` changed) `__pinpointConfig`, the `[data-pinpoint]` host, and `__pinpointOverlayInstalled` were all present. The TASK-22 claim that "reinject swaps the on-new-document bootstrap so reloads use fresh code" holds. Disproved a secondary theory that a second CDP client severs the bridge session (Chrome 149 multiplexes the per-page endpoint; bridge stayed connected, overlay survived). | The original report was almost certainly a flawed/stale-build observation, not a code defect — no fix landed.
